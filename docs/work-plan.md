# Priority Todo 作業計画書

## この文書の扱い

- 今後の実装作業では、着手前に必ずこの作業計画書を読み、現在の実装状況と比較してから作業する。
- 作業後は、実装内容がこの計画に沿っているかを確認する。
- 方針が変わった場合は、実装だけでなくこの計画書も更新する。
- この文書は、UI改善、基本機能改善、Moodle連携、非Moodleユーザー対応の優先順位をそろえるための基準とする。
- フェーズごとの具体的な作業範囲、完了条件、検証観点は `docs/phase-implementation-roadmap.md` を参照する。

## プロダクト方針

Priority Todo は、汎用Todoアプリや汎用カレンダーの代替ではなく、学生向けの課題管理アプリとして育てる。

主な価値は次の通り。

1. 時間割と課題を結びつける。
2. 今日やるべき課題をわかりやすく表示する。
3. Moodle対応大学では、MoodleカレンダーURLや `.ics` ファイルから課題候補を取り込む。
4. Moodle非対応大学でも、手入力、繰り返し、授業ごとの課題テンプレートで十分に使えるようにする。
5. Googleカレンダーと競合する予定表ではなく、課題を整理して行動に変えるアプリにする。

## UI改善方針

現状の課題は、機能以前にチープ感と複雑さが目立つこと。最低ラインとして、App Store に掲載されている品質の高い個人開発アプリのような完成度を目指す。

UIの参考URL、共有画像、モーション、部品設計、ガラス風UI、課題作成画面の方向性は `docs/ui-design-analysis-report.md` も参照する。

### デザイン原則

- 余白を広く取り、情報を詰め込みすぎない。
- タイポグラフィの階層を明確にする。
- 角丸、影、色、カード余白を統一する。
- 白、淡いグレー、青紫系アクセントを中心に、清潔で学生向けの印象にする。
- 下部ナビや主要操作には、控えめなガラス風UIを検討する。
- 参考にしたCSSアニメーションのように、柔らかい移動、拡大縮小、押し込み、軽い弾みを取り入れる。
- 粒子表現は常時表示しない。完了時や今日の課題を終えたときなど、達成感の瞬間だけ控えめに使う。
- `prefers-reduced-motion` に配慮し、アニメーションを苦手とするユーザーを妨げない。

### 優先して直すUI

1. ホーム / 今日画面
2. 課題カード
3. 下部ナビゲーション
4. 課題追加フォーム
5. 時間割タブ
6. 完了済み・空状態表示
7. Moodle取り込み画面

## 基本機能改善方針

### 課題追加フォーム

フォームは、最初に見える項目を絞る。

基本項目は次の通り。

- 課題名
- 授業
- 締切日
- 締切時刻
- いつから取りかかる？
- 提出先URL
- メモ

次の項目は詳細設定または後回しにする。

- 通知アラーム
- 最優先
- 複雑な繰り返し
- 汎用予定表としての時間枠予定

### 用語整理

- 「やること」より「課題」を主軸にする。
- 「タスク開始日」は「いつから取りかかる？」に変更する。
- 「URL」は「提出先URL」や「資料URL」として意味を明確にする。
- 「通知アラーム」は、実装が安定するまで説明を追加するか詳細設定に移す。

### 完了体験

- チェックしたら即座に跡形もなく消える体験は避ける。
- 完了時は「完了しました」「元に戻す」を出す。
- 完了アニメーションは短く、安心感を優先する。
- 削除と完了は明確に区別する。

### 非Moodleユーザー対応

Moodle連携が使えない大学でも、アプリとして成立することを必須条件にする。

重要機能は次の通り。

- 時間割ベースの課題登録
- 授業ごとの課題テンプレート
- 毎週・隔週・毎月などの繰り返し課題
- 授業日基準の締切設定
- いつから取りかかるかの自動初期値
- 手入力の速さ
- 提出先URLの保存

## Moodle連携方針

Moodle連携は強力な差別化要素にする。ただし、Moodle専用アプリにはしない。

### 対応軸

- Moodle対応大学: MoodleカレンダーURLまたは `.ics` ファイルで課題候補をほぼ自動取り込みする。
- その他大学: 繰り返し課題、授業テンプレート、手入力でしっかり対応する。

### 入力方法

まずは `.ics` ファイルアップロードから始める。安定後に MoodleカレンダーURL同期を追加する。

- `.ics` ファイル取り込みは、CORS問題やトークン保存リスクが少ない。
- URL同期は便利だが、`authtoken` を含むURLを秘密情報として扱う必要がある。

### Moodle ICSから読める情報

実サンプルでは、主に次の情報が取れる。

- `UID`: 重複判定・同期キー
- `SUMMARY`: 課題名・分類元
- `DESCRIPTION`: メモ、締切表記、URL抽出元
- `LAST-MODIFIED`: Moodle側更新検知
- `DTSTART` / `DTEND`: 締切または開始日時
- `CATEGORIES`: Moodleコース / 時間割コードに相当する識別子

一方、次の情報はICSだけでは基本的に取れない前提にする。

- 教科名そのもの
- 曜日・時限
- 教室
- 教員名

### CATEGORIES と時間割番号

Moodle ICS の `CATEGORIES` には `26-4-3001` のような値が入る。重要なのは下4桁で、`26-4-3001` の場合は `3001` を時間割番号として扱う。

ルール:

- `CATEGORIES` から下4桁を抽出して Moodle連携用コードとする。
- 時間割タブで教科を登録するとき、Moodle連携あり / なしを右上付近のトグルで切り替える。
- Moodle連携ありの場合、時間割番号は必須にする。
- Moodle連携なしの場合、時間割番号は任意または非表示にする。
- 既存授業に同じ時間割番号があれば、Moodleイベントを自動でその授業へ分類する。
- 未登録の時間割番号が出た場合は、ユーザーに授業へ紐付けてもらう。

### 教科名マッチング

今回のMoodle ICSでは教科名が直接出ていないため、文字列の80%一致を主軸にしない。

優先順位:

1. `CATEGORIES` の下4桁と、授業に登録された時間割番号の一致
2. ユーザーが過去に紐付けた Moodleカテゴリコード
3. もし教科名らしき文字列が取れる場合のみ、類似度による候補提示

類似度80%以上は自動確定ではなく、候補提示に使う。初回はユーザー承認を挟み、承認後は次回から自動分類する。

### 締切時刻の採用ルール

提出時間のミス防止を最優先する。

- `DTSTART` / `DTEND` / `SUMMARY` / `DESCRIPTION` から締切候補を抽出する。
- 複数の締切候補がある場合、ユーザーには候補一覧を出さず、あり得る候補の中で最も早い時刻を採用する。
- `5月10日一杯`、`当日中`、`終日` は原則 `23:59` として扱う。
- `24:00` は提出ミス防止のため、原則として当日 `23:59` に寄せる。
- 自動推定した日時は取り込み確認画面で通常の締切日時として表示し、必要なら編集できるようにする。
- ユーザーを不安にさせるため、通常UIでは複数候補の詳細比較を表示しない。

### イベント分類ルール

初期分類の目安:

- `提出期限`、`課題`、`レポート`、`ワークシート`、`提出`: 課題候補
- `アンケート終了`: レスポンスカード / アンケート締切候補
- `アンケート開始`: デフォルトでは取り込まない、またはその他扱い
- `受験可能期間の終了`: 小テスト締切候補
- `受験可能期間の開始`: `DESCRIPTION` から締切を抽出できる場合のみ小テスト候補
- `欠席届` などの補助提出口: デフォルトOFF、ユーザーが必要なら取り込む

### URL抽出

ICSではURLが `DESCRIPTION` 内に折り返されて入ることがある。

実装時は iCalendar の行折り返しを復元してからURLを抽出する。

例:

```text
https
	://example.com
```

を

```text
https://example.com
```

に戻す。

URLが取れた場合は、タスクの「提出先URL」として保存する。取れない場合は空でよい。

### 同期

`.ics` 取り込みが安定した後、MoodleカレンダーURL同期を実装する。

基本方針:

- アプリ起動時に同期する。
- 前回同期から一定時間、たとえば6時間または1日以上経過している場合のみ取得する。
- `UID` で同一イベントを判定する。
- `LAST-MODIFIED`、`DTSTART`、`SUMMARY`、`DESCRIPTION` の変化で更新を検出する。
- URL同期前の手動 `.ics` 再取り込みでも同じ判定を使い、新規、更新あり、変更なしを分ける。
- `DTSTAMP` はエクスポート時刻の可能性が高いため、差分判定の主役にはしない。
- Moodleから消えたイベントは自動削除しない。期間外になっただけの可能性があるため、確認対象にする。

未起動時の定期同期は後回しにする。サーバーにMoodleカレンダーURLを保存する場合は、暗号化保存、ログ漏洩防止、削除機能、同期停止機能が必要。

## 作業工程

### Phase 0: 計画書確認と現状比較

- 実装前にこの文書を読む。
- 現在のコードがどのPhaseまで進んでいるか確認する。
- その作業が計画のどこに当たるかを明確にする。

### Phase 1: UI品質の底上げ

- 今日画面の再設計
- 課題カードの刷新
- 下部ナビの改善
- 余白、角丸、影、色、タイポの統一
- 空状態・完了状態の見た目改善
- 軽いマイクロインタラクション追加

### Phase 2: 時間割タブ / 授業登録の再設計

- 授業登録フォームを見直す。
- Moodle連携あり / なしトグルを追加する。
- Moodle連携ありの場合、時間割番号の入力を必須にする。
- 時間割番号は下4桁を正規化して保存する。
- Moodle連携なしの場合、時間割番号を任意または非表示にする。

### Phase 3: 課題追加フォームの簡略化

- 課題名、授業、締切、いつから取りかかる、提出先URL、メモを中心にする。
- 通知、優先度、複雑な繰り返しは詳細設定へ移す。
- 日付・時刻UIを統一する。

### Phase 4: 非Moodle向け繰り返し・テンプレート強化

- 授業ごとの課題テンプレートを設計する。
- 毎週、隔週、毎月、授業日基準の繰り返しを使いやすくする。
- Moodleを使わないユーザーでも課題管理が成立する状態にする。

### Phase 5: Moodle `.ics` ファイル取り込み

- `.ics` アップロード画面を作る。
- iCalendarの行折り返しを復元する。
- `VEVENT` を抽出し、`UID` で重複排除する。
- `SUMMARY`、`DESCRIPTION`、`DTSTART`、`LAST-MODIFIED`、`CATEGORIES` を読む。
- 締切候補から最も早い時刻を採用する。
- イベントを課題、小テスト、アンケート、その他に分類する。

### Phase 6: Moodleコースコード紐付け

- `CATEGORIES` の下4桁を抽出する。
- 登録済み授業の時間割番号と照合する。
- 一致する場合は自動分類する。
- 未登録の場合は、授業へ紐付ける画面を出す。
- 一度紐付けたら次回から自動分類する。

### Phase 7: Moodle取り込み確認画面

- 取り込む候補を一覧表示する。
- デフォルトON/OFFを分類ルールに従って設定する。
- 課題名、締切、授業、提出先URLを編集できるようにする。
- 複数の締切候補は表示せず、採用済みの最も早い日時だけを通常の締切として見せる。

### Phase 8: Moodle URL同期

- MoodleカレンダーURL登録画面を作る。
- URLには認証トークンが含まれる可能性があることを説明する。
- アプリ起動時に同期する。
- 新規イベント、締切変更、タイトル変更、消失候補を検出する。
- 変更は安全側に倒し、勝手に削除しない。

### Phase 9: 完了体験と通知改善

- 完了トーストと元に戻すを追加する。
- 通知アラームの意味を明確化する。
- 通知が未実装または環境依存の場合は、そのことをUIで説明する。
- 将来的に取りかかり日通知、締切前通知、スヌーズを検討する。

### Phase 10: 未起動時同期・外部LMS拡張の検討

- サーバー側定期同期を検討する。
- Moodle URLの暗号化保存とログ漏洩防止を設計する。
- manaba、Google Classroom、WebClassなどは、需要が見えてから個別対応を検討する。
- それまでは非Moodle向けの汎用機能を優先する。

## 実装時の注意

- Moodle連携は便利だが、Moodle非対応ユーザーを置き去りにしない。
- 時間割番号はMoodle連携ありの場合のみ必須にする。
- 締切時刻は常に安全側、つまり早い方に倒す。
- 勝手に削除する挙動は避ける。
- MoodleカレンダーURLは秘密情報として扱う。
- UIは機能追加よりも、まず信頼感と直感性を優先する。
