# Priority Todo フェーズ別実装ロードマップ

作成日: 2026-05-17

## この文書の目的

この文書は、Priority Todo の今後の実装をフェーズ単位で進めるための実行ロードマップである。

`docs/work-plan.md` はプロダクト全体の方針、`docs/ui-design-analysis-report.md` はUI判断の根拠、この文書は「次にどのフェーズで何を実装し、何をもって完了とするか」を扱う。

実装時は `WORKFLOW.md` に従い、各フェーズを commit / push / PR / merge / main同期 / 報告まで完了してから、ユーザー確認を待つ。

## 現在の前提

2026-05-17 時点のコード確認では、次の状態になっている。

- 課題作成フォームには、締切、開始日、提出先URL、メモ、詳細設定、繰り返し、通知、最優先が存在する。
- ただし、`課題 / 時間が決まった予定` の切り替えが残っており、課題専用アプリとしての焦点が少しぼやけている。
- `いつから取りかかる？` はあるが、ユーザーが望む `課題に取り組む期間` という表現と、`開始日時から締切まで` の見せ方にはまだ寄っていない。
- 今日画面は期限超過、今日締切、最優先などの状態表示を持つが、「なぜ今日表示されているか」の説明はまだ弱い。
- 時間割登録では Moodle連携ON時の4桁コード必須判定が実装されているが、UI導線と説明はさらに整えられる。
- Moodle `.ics` 取り込みは、UID重複排除、CATEGORIES下4桁照合、分類、締切推定、URL抽出まで進んでいる。
- Moodle取り込み確認画面は候補選択までで、課題名、締切、授業、提出先URLの編集はまだ弱い。
- 祝日スキップ設定は存在するが、授業日基準の繰り返し課題で本当に期待どおり効くかは検証フェーズが必要。
- カレンダーは横スワイプで月切り替えできるが、指に追従する滑らかな移動ではない。

## 実装順の考え方

以前の大方針では、UI品質改善、時間割、課題追加フォーム、非Moodle、Moodleの順に整理していた。

ただし、直近の議論では「今UIとして一番課題なのはタスク生成画面」という認識になったため、実装順は次のように再整理する。

1. 課題作成画面を最初に直し、アプリの入力体験を整える。
2. 今日画面と課題カードで、なぜ表示されているかを見えるようにする。
3. 下部ナビ、プラスボタン、カレンダーの動きを整え、アプリ全体のチープ感を減らす。
4. 時間割登録と非Moodle向けテンプレートを強化し、Moodle非対応ユーザーも使える状態にする。
5. Moodle取り込み確認、紐付け、URL同期へ進む。

## Phase 1: 課題作成画面の再設計

### 目的

Priority Todo の最重要入力導線を、課題専用で見やすい画面にする。

このフェーズは、UI品質改善と課題追加フォーム簡略化を兼ねる。ユーザーが最も気にしている「タスク生成画面」を最初に直す。

### やること

- `課題 / 時間が決まった予定` の切り替えを課題作成画面から廃止する。
- タスクタブのプラスボタンから開く画面は、課題作成専用にする。
- 予定追加はカレンダー側の導線へ寄せる。
- 画面構成を次の順に整理する。

```text
キャンセル        新しい課題        保存

課題名

授業

締切
2026/05/15（金） 16:00

課題に取り組む期間
2026/05/13（水）16:00 から締切まで

最優先

提出先URL

メモ

詳細設定
繰り返し / 通知 / テンプレート化
```

- `いつから取りかかる？` を `課題に取り組む期間` に変更する。
- 表示は `YYYY/MM/DD（曜）HH:mm から締切まで` に寄せる。
- 開始日時選択ではミニカレンダーを出す。
- 締切より後の日付は選択不可にする。
- 終了日は原則として締切と一致させ、通常UIでは別入力させない。
- `最優先` は締切エリアではなく、取り組む期間エリアの下に置く。
- `提出先URL` はメモより上に置く。
- 詳細設定は必ず下部に置き、繰り返し、通知、テンプレート化を格納する。
- 編集画面も新規作成画面と同じ構造にする。

### やらないこと

- このフェーズではMoodle同期やURL同期は作らない。
- このフェーズでは授業テンプレートの永続化までは作らない。
- 予定機能をデータモデルから削除するかは、このフェーズでは決めない。

### 完了条件

- 新規課題作成と既存課題編集が同じUIで操作できる。
- 初見でも、課題名、授業、締切、取り組む期間、URL、メモの順に迷わず入力できる。
- 締切後の開始日は選べない。
- 詳細設定が下部にあり、基本入力を邪魔しない。
- モバイル幅でテキストが詰まらない。

### 検証

- `npx tsc --noEmit`
- `npm run build`
- 可能ならローカルブラウザで以下を確認する。
  - 新規課題を保存できる。
  - 既存課題を編集できる。
  - 開始日が締切後にできない。
  - 詳細設定を開閉できる。
  - URLとメモが保存される。

## Phase 2: 今日画面と課題カードの信頼性改善

### 目的

ユーザーが「なぜこの課題が今日表示されているのか」を理解できるようにする。

### やること

- 課題カードに表示理由を出す。
- 表示理由の例を整備する。

```text
今日から表示
締切まで2日
締切日当日
期限超過
最優先
毎週火曜
Moodleから追加
```

- 締切、取り組み開始日、授業名、繰り返し情報の見せ方を整理する。
- 色数を減らし、警告色は期限超過や削除などに限定する。
- 課題カードの角丸、影、余白、文字サイズを統一する。
- 完了ボタンを見つけやすくし、誤タップしにくくする。
- 完了後に短いトーストと `元に戻す` を出す。

### やらないこと

- 通知の本格実装はしない。
- 大規模なデータ構造変更はしない。

### 完了条件

- 今日画面の各課題に、表示理由または優先理由が出る。
- 完了してもユーザーがすぐ戻せる。
- 締切、授業、状態ラベルの階層が見やすい。
- カードの装飾が過剰でない。

### 検証

- `npx tsc --noEmit`
- `npm run build`
- 今日締切、期限超過、最優先、繰り返し、Moodle由来の課題を表示確認する。

### 将来課題: PWA / アプリ化時の下部 safe area 調整

PWAとしてホーム画面追加した状態では、iOSのホームインジケータ用 safe area と下部ナビの余白処理により、画面下端に白い余白やデッドスペースが残って見える場合がある。

現時点ではブラウザ表示との互換性と操作部品の見切れ防止を優先し、下部ナビのsafe area処理は大きく変更しない。アプリ化またはPWA専用UIを本格調整する段階で、通常ブラウザ表示とPWA表示を分岐し、次の方針で再検討する。

- 通常ブラウザ表示では、ブラウザUIや可変ビューポートに隠れないよう安全側の余白を維持する。
- PWA表示では、背景を画面下端まで塗り、操作できるアイコン・ラベルだけがホームインジケータに被らない最小余白を残す。
- `display-mode: standalone` と iOS の `navigator.standalone` を使い、必要なら `pwa-mode` のようなclassでCSSを分岐する。
- 下部ナビ、全画面フォーム、FAB、スクロール領域の `env(safe-area-inset-bottom)` を一括で見直す。
- 実機PWAで、アイコンやラベルが見切れず、タップ領域がホームインジケータと干渉しないことを確認する。

## Phase 4: 時間割・授業登録の再設計

### 目的

Moodleユーザーにも非Moodleユーザーにも、負担の少ない授業登録を提供する。

### やること

- 授業登録フォームの情報順を整理する。

```text
授業名
曜日
時限
教室
教員名
色
Moodle連携
時間割番号 / Moodleコースコード
メモ
```

- Moodle連携ONなら時間割番号を必須にする。
- Moodle連携OFFなら時間割番号は任意、または非表示寄りにする。
- コード入力時は4桁に正規化する。
- 保存時だけでなく、入力中にも必須状態がわかるようにする。
- `26-4-3001` の場合は `3001` だけ入力することを説明する。
- 授業色の選択UIを見やすくする。
- 登録済み授業から、未完了課題数やMoodle連携状態が見えるようにする。

### やらないこと

- Moodle URL同期はまだ実装しない。
- 大学別時間割テンプレート共有はまだ作らない。

### 完了条件

- Moodle連携ONでコード未入力なら保存できない。
- Moodle連携OFFならコードなしでも保存できる。
- 授業名、曜日、時限、教室、教員名、色が自然に入力できる。
- 既存授業の編集でも同じルールが効く。

### 検証

- `npx tsc --noEmit`
- `npm run build`
- Moodle連携ON/OFFの保存挙動を確認する。
- 時間割から作られる授業カテゴリが壊れていないか確認する。

## Phase 5: 非Moodle向け繰り返し・テンプレート強化

### 目的

Moodleを使わない大学でも、毎週課題や授業日基準の課題を楽に扱えるようにする。

### やること

- 授業ごとの課題テンプレートを保存できるようにする。
- テンプレート例を扱えるようにする。

```text
この授業は毎週レスポンスカード
授業当日23:59締切
授業前日から表示
祝日は休講としてスキップ
```

- 毎週、隔週、授業日基準、締切オフセットを整理する。
- `毎週この曜日に課題がある` と `授業がある日に課題がある` を区別する。
- 授業日基準の場合だけ、祝日スキップを適用する。
- オンデマンド授業は祝日スキップしない。
- 生成された繰り返し課題には `第1回`、`第2回` のような回数を表示し、締切のズレに気づきやすくする。
- 祝日スキップが効くか重点検証する。

### やらないこと

- 大学別の正式な学事カレンダー連携はまだ作らない。
- 友人共有やテンプレートマーケットのような成長機能はまだ作らない。

### 完了条件

- 授業単位でテンプレートを作成/編集/削除できる。
- テンプレートから課題を作れる。
- 祝日授業の扱いがUI上で理解できる。
- 授業日が祝日の場合、授業日基準課題が不自然に生成されない。

### 検証

- `npx tsc --noEmit`
- `npm run build`
- 祝日をまたぐ毎週課題、隔週課題、オンデマンド課題を確認する。
- 繰り返し課題が今日画面、カレンダー、完了済みで `第n回` として表示されるか確認する。

## Phase 6: Moodle ICS取り込み確認画面の強化

### 目的

Moodle `.ics` 取り込みを、ユーザーが安心して確認・修正できる状態にする。

### やること

- 候補ごとに次を編集できるようにする。

```text
課題名
締切
授業
提出先URL
メモ
取り込む / 取り込まない
```

- UID重複排除の結果をわかりやすくする。
- CATEGORIES下4桁と授業の自動一致を表示する。
- 未紐付けコードを目立たせる。
- 課題、小テスト、アンケート、その他の分類を見やすくする。
- 締切候補が複数ある場合は、採用済みの最も早い締切だけを通常UIに表示する。
- 必要ならユーザーが締切を修正できるようにする。

### やらないこと

- Moodle URLの自動同期はまだ作らない。
- Moodleから消えたイベントの自動削除はしない。

### 完了条件

- 取り込み前に課題名、締切、授業、URLを確認できる。
- 誤分類や締切推定ミスをユーザーが修正できる。
- 取り込み済み候補を重複追加しない。

### 検証

- `npx tsc --noEmit`
- `npm run build`
- サンプル `.ics` で、分類、締切、URL、CATEGORIES紐付け、重複排除を確認する。

## Phase 7: Moodleコースコード紐付けと連携タブ整理

### 目的

初回取り込み時に未登録コードが出ても、次回から自動分類できるようにする。

### やること

- `CATEGORIES` から抽出した4桁コードを時間割番号と照合する。
- 一致すれば自動分類する。
- 未登録コードが出た場合、授業へ割り当てる画面を作る。
- 一度割り当てたコードは次回から自動分類する。
- `連携` タブ内に次の情報を整理する。

```text
ICSファイル取り込み
未分類コードの割り当て
将来のURL同期
同期状態
秘密情報に関する注意
```

### やらないこと

- サーバー定期同期はまだ作らない。
- Moodle以外のLMS個別対応はまだ作らない。

### 完了条件

- 未紐付けコードを既存授業へ割り当てられる。
- 割り当て後、同じコードの候補は自動で授業に入る。
- `連携` タブがMoodle専用に見えすぎない。

### 検証

- `npx tsc --noEmit`
- `npm run build`
- 未登録コードありの `.ics` を取り込み、割り当て後の再取り込みで自動分類されるか確認する。

## Phase 8: Moodle URL同期

### 目的

`.ics` ファイル手動取り込みの次に、MoodleカレンダーURLからの同期を検討・実装する。

### やること

- MoodleカレンダーURL登録画面を作る。
- URLに秘密トークンが含まれる可能性を説明する。
- URLを秘密情報として扱う。
- アプリ起動時同期を実装する。
- 前回同期から一定時間が経過した場合だけ取得する。
- UIDで同一イベントを判定する。
- `LAST-MODIFIED`、`DTSTART`、`SUMMARY`、`DESCRIPTION` などの変化で更新を検出する。
- 新規課題、締切変更、タイトル変更を確認対象にする。
- 消失イベントは自動削除せず、確認対象にする。
- 同期停止/URL削除導線を作る。

### やらないこと

- 未起動時のサーバー定期同期はまだ作らない。
- URLや同期結果をログに不用意に出さない。

### 完了条件

- URL登録、同期、停止、削除ができる。
- 新規課題と締切変更を検出できる。
- URLが秘密情報であることがUI上で明示される。
- 消えたイベントを勝手に削除しない。

### 検証

- `npx tsc --noEmit`
- `npm run build`
- URLを保存/削除できるか確認する。
- 同期結果で新規/変更/消失候補が分かれるか確認する。
- 秘密URLが画面やログに不用意に露出しないか確認する。

## Phase 9: 完了体験・通知・定期同期

### 目的

課題管理アプリとして、提出忘れ防止と安心感を強化する。

### やること

- 完了トーストと `元に戻す` を安定させる。
- 完了アニメーションを控えめに追加する。
- 通知許可の導線を設計する。
- 締切前通知と取りかかり日通知を整理する。
- 通知がブラウザ環境依存である場合はUI上で説明する。
- サーバー定期同期を行う場合の設計を検討する。
- 未起動時同期を行う場合は、Moodle URLの保存方法、暗号化、ログ漏洩防止、削除機能を先に設計する。

### やらないこと

- 通知やサーバー同期は、秘密情報の扱いが固まるまで無理に実装しない。
- 本番ユーザーデータを読んだり、横断集計したりしない。

### 完了条件

- 完了/復元が安心して使える。
- 通知の意味と制約がユーザーに伝わる。
- サーバー定期同期を実装する場合の安全条件が明文化されている。

### 検証

- `npx tsc --noEmit`
- `npm run build`
- 完了、復元、通知設定、同期設定を確認する。
- 秘密情報や本番ユーザーデータの扱いに問題がないか確認する。

- 空状態の文言を整える。
- ヘルプ内容を最新仕様に合わせる。
- 共有リンク、時間割共有、将来の授業テンプレート共有を検討する。
- App Store品質に近い余白、タイポ、色、動きの最終調整をする。

### やらないこと

- 広告や収益化は、継続率と利用頻度が見えるまで急がない。
- Moodle以外のLMS個別最適化は、需要が見えてから検討する。

### 完了条件

- 初回ユーザーが、時間割登録、課題作成、今日画面確認まで迷わず進める。
- Moodleユーザーと非Moodleユーザーの導線が分かれている。
- 主要な空状態が自然な説明になっている。
- 公開前に見た目の粗さが目立たない。

### 検証

- `npx tsc --noEmit`
- `npm run build`
- 初回状態、データあり状態、空状態、モバイル幅を確認する。

## フェーズ横断の注意

### データとセキュリティ

- Firestoreの本番ユーザーデータを読まない。
- `.env`、サービスアカウント、秘密URLを開かない。
- MoodleカレンダーURLは秘密情報として扱う。
- Firestore Rulesを緩めない。

### UI

- 余白、角丸、影、色、タイポをそろえる。
- ガラス風UIはナビ、ツールバー、シートなど役割が明確な場所に限定する。
- モーションは状態変化の説明に使う。
- `prefers-reduced-motion` に配慮する。
- カード内カードを増やさない。

### 機能

- Priority Todoは汎用カレンダーではなく、学生向け課題管理アプリとして育てる。
- Moodleユーザーには強い自動化を提供する。
- 非Moodleユーザーにも、時間割、繰り返し、テンプレート、手入力で十分使える状態を提供する。
- 締切推定は安全側、つまり早い時刻を採用する。
- 自動生成・自動分類の理由をUI上で説明する。
